    Modelo de dados do AvaliaAí UnB (Supabase / PostgreSQL)

    Issue #109. Depende da #90 (esquema versionado em docs/migrations/). Este documento descreve o esquema atual e propõe a tabela de comentários. Nada aqui foi aplicado no banco.

    1. Visão geral

    O banco tem cinco tabelas e uma view. Três são alimentadas pelo scraper do SIGAA (professores, disciplinas, turmas) e duas pelos usuários autenticados (perfis, avaliacoes).

    erDiagram
    auth_users ||--o| perfis : "id"
    perfis ||--o{ avaliacoes : "usuario_id"
    professores ||--o{ turmas : "professor_id"
    disciplinas ||--o{ turmas : "disciplina_id"
    professores ||--o{ avaliacoes : "professor_id"
    disciplinas ||--o{ avaliacoes : "disciplina_id"

    professores {
        bigint id PK
        varchar nome
        varchar departamento
        timestamptz criado_em
    }
    disciplinas {
        bigint id PK
        varchar codigo UK
        varchar nome
        timestamptz criado_em
    }
    turmas {
        bigint id PK
        bigint professor_id FK
        bigint disciplina_id FK
        int ano
        int periodo
        timestamptz criado_em
    }
    perfis {
        uuid id PK, FK
        varchar username UK
        varchar nome_completo
        timestamptz criado_em
    }
    avaliacoes {
        bigint id PK
        uuid usuario_id FK
        bigint professor_id FK
        bigint disciplina_id FK
        int ano
        int periodo
        int didatica
        int clareza
        int organizacao
        int disponibilidade
        int dificuldade
        timestamptz criado_em
    }

    2. Tabelas

    2.1 professores

    Alimentada pelo scraper do SIGAA.

    Coluna Tipo Restrições
    id BIGINT PK, GENERATED BY DEFAULT AS IDENTITY
    nome VARCHAR(255) NOT NULL
    departamento VARCHAR(255) NOT NULL, default ''
    criado_em TIMESTAMPTZ default NOW()
    • Unicidade: uq_professores_nome_departamento em (nome, departamento).

    2.2 disciplinas

    Alimentada pelo scraper do SIGAA.

    Coluna Tipo Restrições
    id BIGINT PK, identity
    codigo VARCHAR(50) NOT NULL
    nome VARCHAR(255) NOT NULL
    criado_em TIMESTAMPTZ default NOW()
    • Unicidade: uq_disciplinas_codigo em (codigo).

    2.3 turmas

    Vínculo entre professor e disciplina em um semestre. Alimentada pelo scraper.

    Coluna Tipo Restrições
    id BIGINT PK, identity
    professor_id BIGINT NOT NULL, FK → professores(id) ON DELETE CASCADE
    disciplina_id BIGINT NOT NULL, FK → disciplinas(id) ON DELETE CASCADE
    ano INTEGER NOT NULL
    periodo INTEGER NOT NULL, CHECK (periodo BETWEEN 1 AND 4)
    criado_em TIMESTAMPTZ default NOW()
    • Unicidade: uq_turmas_prof_disc_ano_periodo em (professor_id, disciplina_id, ano, periodo). É a chave usada pelo scraper para não duplicar turmas.

    2.4 perfis

    Dados públicos do usuário, ligados ao Supabase Auth.

    Coluna Tipo Restrições
    id UUID PK, FK → auth.users(id) ON DELETE CASCADE
    username VARCHAR(30) NOT NULL
    nome_completo VARCHAR(100) NOT NULL
    criado_em TIMESTAMPTZ default NOW()
    • Unicidade: uq_perfis_username em (username).

    2.5 avaliacoes

    Avaliação por critérios objetivos, com notas inteiras de 1 a 5.

    Coluna Tipo Restrições
    id BIGINT PK, identity
    usuario_id UUID NOT NULL, FK → perfis(id) ON DELETE CASCADE
    professor_id BIGINT NOT NULL, FK → professores(id) ON DELETE CASCADE
    disciplina_id BIGINT NOT NULL, FK → disciplinas(id) ON DELETE CASCADE
    ano INTEGER NOT NULL
    periodo INTEGER NOT NULL, CHECK (periodo BETWEEN 1 AND 4)
    didatica INTEGER NOT NULL, CHECK (1..5)
    clareza INTEGER NOT NULL, CHECK (1..5)
    organizacao INTEGER NOT NULL, CHECK (1..5)
    disponibilidade INTEGER NOT NULL, CHECK (1..5)
    dificuldade INTEGER NOT NULL, CHECK (1..5)
    criado_em TIMESTAMPTZ default NOW()
    • Unicidade: uq_avaliacoes_usuario_prof_disc em (usuario_id, professor_id, disciplina_id). Cada usuário avalia uma vez cada combinação professor + disciplina. Como ano e periodo não entram na chave, não é possível reavaliar a mesma combinação em outro semestre.

    2.6 View vw_professor_disciplina

    Junta turmas, professores e disciplinas para consulta direta.

    Coluna Origem
    turma_id turmas.id
    professor_id turmas.professor_id
    professor professores.nome
    departamento professores.departamento
    disciplina_id turmas.disciplina_id
    codigo_disciplina disciplinas.codigo
    disciplina disciplinas.nome
    ano turmas.ano
    periodo turmas.periodo

    Definição (conferida no banco com pg_get_viewdef):

    SELECT t.id AS turma_id,
       t.professor_id,
       p.nome AS professor,
       p.departamento,
       t.disciplina_id,
       d.codigo AS codigo_disciplina,
       d.nome AS disciplina,
       t.ano,
       t.periodo
  FROM turmas t
  JOIN professores p ON p.id = t.professor_id
  JOIN disciplinas d ON d.id = t.disciplina_id;

    Atenção: por padrão, uma view no PostgreSQL executa com as permissões do dono, não de quem consulta, e por isso pode contornar o RLS das tabelas de base. Hoje isso é aceitável porque as três tabelas são dados públicos do SIGAA. Se a view passar a expor dados sensíveis, usar WITH (security_invoker = true) (PostgreSQL 15+).

    3. Cascatas

    Ao apagar... Também é apagado
    auth.users perfis → avaliacoes do usuário
    perfis avaliacoes do usuário
    professores turmas e avaliacoes do professor
    disciplinas turmas e avaliacoes da disciplina

    Consequência prática: o scraper não deve apagar professores ou disciplinas para "refazer" a carga, pois isso destrói as avaliações associadas. Deve usar upsert pelas chaves únicas acima.

    4. Chave de unicidade do professor e efeito nas buscas

    O professor é identificado por (nome, departamento), não só pelo nome.

    O departamento guardado em professores é a unidade que oferece a disciplina no SIGAA, e não necessariamente o departamento de lotação do docente. Por isso:

    • Um mesmo docente que leciona disciplinas ofertadas por departamentos diferentes pode aparecer como mais de um registro em professores, cada um com seu id e suas próprias avaliações.
    • Dois docentes homônimos em departamentos diferentes são tratados como pessoas distintas, o que pode estar certo ou errado.
    • Uma busca apenas por nome pode retornar vários registros para a mesma pessoa. A interface deve exibir o departamento ao lado do nome, e a busca não deve assumir que o nome é único.
    • Médias de avaliação são calculadas por registro, então um docente dividido em dois registros terá notas separadas.

    Limitação conhecida: não existe hoje uma identificação única do docente (como matrícula). Unificar registros duplicados seria uma decisão futura.

    5. Políticas de RLS

    Consultas executadas no SQL Editor do Supabase:

    -- Tabelas com RLS ativo
SELECT c.relname, c.relrowsecurity, c.relforcerowsecurity
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r';

-- Políticas
SELECT tablename, policyname, permissive, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;

    Resultado

    Tabela RLS ativo FORCE RLS Políticas
    professores sim não nenhuma
    disciplinas sim não nenhuma
    turmas sim não nenhuma
    perfis sim não nenhuma
    avaliacoes sim não nenhuma

    O que isso significa

    • Com RLS ativo e nenhuma política, o PostgreSQL nega todo acesso aos papéis anon e authenticated. Um cliente que use a chave pública (anon key) ou o token de um usuário logado não consegue ler nem escrever em nenhuma tabela.
    • A service_role (chave secreta) ignora o RLS, e é por ela que a aplicação Flask lê e grava (ver "Como a aplicação acessa o banco" abaixo).
    • FORCE RLS está desligado, então o dono das tabelas (papel postgres) também ignora as políticas.
    • Consequência: hoje toda a segurança depende de o acesso passar pelo backend com a service_role. A chave service_role nunca pode ir para o frontend nem para o repositório.

    Privilégios e a view vw_professor_disciplina

    Consulta usada:

    SELECT grantee, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'public' AND table_name = 'vw_professor_disciplina';

    Resultado: postgres, anon, authenticated e service_role têm todos os privilégios (SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER) sobre a view. Esse é o padrão do Supabase para objetos criados no schema public; ninguém concedeu isso explicitamente.

    Efeitos:

    • Leitura aberta. Uma view executa com as permissões do dono (postgres), que ignora o RLS. Como anon tem SELECT, qualquer pessoa com a chave pública (anon key) consegue consultar a view e ler professores, departamentos, disciplinas e turmas, apesar de as tabelas de base estarem bloqueadas pelo RLS. As tabelas perfis e avaliacoes não são expostas, pois não entram na view.
    • Escrita. Os privilégios de INSERT/UPDATE/DELETE constam, mas a view faz JOIN de três tabelas e, por isso, o PostgreSQL não a trata como atualizável. Na prática, as escritas falham.
    • Dados envolvidos. São dados públicos do SIGAA, então a leitura aberta pode ser aceitável ou até desejada (por exemplo, para a busca funcionar sem login). O ponto é que isso deve ser uma decisão consciente, e hoje parece ser consequência do padrão do Supabase.
    • Não é usada pela aplicação. O backend só usa a service_role (ver abaixo), então a leitura anônima da view não é necessária para o funcionamento atual. Ela existe apenas porque o Supabase concede os privilégios por padrão.

    Opções para o grupo avaliar (não aplicadas):

    -- Opção A: manter a leitura pública, mas só leitura (remove privilégios de escrita)
REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
    ON vw_professor_disciplina FROM anon, authenticated;

-- Opção B: restringir a leitura a usuários logados
REVOKE ALL ON vw_professor_disciplina FROM anon;

-- Opção C: fazer a view respeitar o RLS de quem consulta (PostgreSQL 15+).
-- Exige criar políticas de SELECT nas três tabelas de base, senão a view passa a retornar vazio.
ALTER VIEW vw_professor_disciplina SET (security_invoker = true);

    Recomendação: a opção B (ou uma variação que revogue de anon e authenticated), pois o backend usa a service_role, que não é afetada por REVOKE. Antes de aplicar, buscar no repositório por vw_professor_disciplina e conferir que nenhum código a consulta com outra chave.

    Como a aplicação acessa o banco

    Pelo .env_example e pelo módulo supabase_db.py:

    • A aplicação é um backend Flask. As variáveis são SECRET_KEY, SUPABASE_URL, SUPABASE_SERVICE_KEY e FLASK_DEBUG.
    • O cliente Supabase é criado somente com a SUPABASE_SERVICE_KEY. Não há anon key na configuração.
    • O próprio código documenta que a service key fica só no servidor, nunca em templates.
    • Existe um segundo cliente (novo_cliente) usado para validar a senha de um usuário sem alterar o cliente principal.

    Consequências:

    1. O RLS não protege o caminho da aplicação, pois a service_role o ignora. Toda regra de autorização (quem pode editar ou apagar o quê) é responsabilidade do código Flask.
    2. O RLS sem políticas funciona como trava de segurança: se alguém usar a anon key ou um token de usuário diretamente contra a API do Supabase, não consegue ler nem escrever nas tabelas. A única exceção é a view, tratada acima.
    3. Políticas que usam auth.uid() só teriam efeito se um cliente acessasse o Supabase com o token do usuário, o que a aplicação atual não faz.

    Divergência entre o script do repositório e o banco

    O banco real tem RLS ativo nas cinco tabelas, mas o script de docs/migrations/ não contém nenhum ENABLE ROW LEVEL SECURITY. Quem recriar o banco só com o script obtém tabelas com RLS desligado e, pelos privilégios padrão do Supabase, legíveis e graváveis por anon com a chave pública. Isso contradiz o critério da #90 de que o script recria o esquema, e abre o banco.

    Proposta de acréscimo ao final do script (idempotente; o banco atual já está assim, então não muda nada nele):

    -- PROPOSTA: não aplicar sem aprovação do grupo.
ALTER TABLE professores ENABLE ROW LEVEL SECURITY;
ALTER TABLE disciplinas ENABLE ROW LEVEL SECURITY;
ALTER TABLE turmas      ENABLE ROW LEVEL SECURITY;
ALTER TABLE perfis      ENABLE ROW LEVEL SECURITY;
ALTER TABLE avaliacoes  ENABLE ROW LEVEL SECURITY;

-- Sem políticas: acesso apenas pela service_role (backend e scraper).
-- Opcional, mas recomendado: tirar os privilégios padrão dos papéis públicos.
REVOKE ALL ON professores, disciplinas, turmas, perfis, avaliacoes
    FROM anon, authenticated;
REVOKE ALL ON vw_professor_disciplina FROM anon, authenticated;

    6. Proposta: tabela comentarios

    Status: proposta para revisão do grupo. SQL não aplicado.

    6.1 Decisões de projeto

    Tema Proposta Motivo
    Ligação com usuário usuario_id → perfis(id) Mesmo padrão de avaliacoes.
    Ligação com professor professor_id → professores(id), NOT NULL O comentário é sempre sobre um professor.
    Ligação com disciplina disciplina_id → disciplinas(id), opcional Permite comentar o professor em geral ou numa disciplina específica.
    Quantidade por usuário 1 comentário por usuário por professor Evita spam e mantém o comentário como complemento da avaliação.
    Exclusão ON DELETE CASCADE em usuário e professor; SET NULL em disciplina Segue o padrão do esquema, sem perder o comentário se a disciplina sumir.
    Tamanho do texto de 10 a 1000 caracteres Evita comentários vazios e textos gigantes.
    Edição atualizado_em mantido por trigger Mostra se o comentário foi editado.

    6.2 SQL proposto

    -- PROPOSTA: não aplicar sem aprovação do grupo.

CREATE TABLE IF NOT EXISTS comentarios (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    usuario_id UUID NOT NULL REFERENCES perfis(id) ON DELETE CASCADE,
    professor_id BIGINT NOT NULL REFERENCES professores(id) ON DELETE CASCADE,
    disciplina_id BIGINT REFERENCES disciplinas(id) ON DELETE SET NULL,
    texto TEXT NOT NULL,
    criado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    atualizado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_comentarios_texto_tamanho
        CHECK (char_length(btrim(texto)) BETWEEN 10 AND 1000),
    CONSTRAINT uq_comentarios_usuario_professor UNIQUE (usuario_id, professor_id)
);

-- Listagem dos comentários de um professor, do mais recente ao mais antigo
CREATE INDEX IF NOT EXISTS idx_comentarios_professor_criado
    ON comentarios (professor_id, criado_em DESC);

-- Mantém atualizado_em
CREATE OR REPLACE FUNCTION set_atualizado_em()
RETURNS TRIGGER AS $$
BEGIN
    NEW.atualizado_em = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_comentarios_atualizado_em
    BEFORE UPDATE ON comentarios
    FOR EACH ROW EXECUTE FUNCTION set_atualizado_em();

-- RLS
ALTER TABLE comentarios ENABLE ROW LEVEL SECURITY;

-- Leitura pública (ajustar para "to authenticated" se o grupo preferir).
-- Atenção: as demais tabelas não têm política; os comentários seriam os primeiros.
CREATE POLICY comentarios_select_publico
    ON comentarios FOR SELECT
    TO anon, authenticated
    USING (true);

-- Só o próprio usuário cria comentário em seu nome
CREATE POLICY comentarios_insert_proprio
    ON comentarios FOR INSERT
    TO authenticated
    WITH CHECK (auth.uid() = usuario_id);

-- Só o autor edita
CREATE POLICY comentarios_update_proprio
    ON comentarios FOR UPDATE
    TO authenticated
    USING (auth.uid() = usuario_id)
    WITH CHECK (auth.uid() = usuario_id);

-- Só o autor apaga
CREATE POLICY comentarios_delete_proprio
    ON comentarios FOR DELETE
    TO authenticated
    USING (auth.uid() = usuario_id);

    6.3 Pontos para o grupo decidir

    1. Um por professor ou um por professor + disciplina? A proposta usa um por professor. Para um por disciplina, trocar a unicidade por (usuario_id, professor_id, disciplina_id) e tornar disciplina_id NOT NULL.
    2. Exigir avaliação antes de comentar? Seria possível acrescentar ao WITH CHECK do insert um EXISTS (SELECT 1 FROM avaliacoes ...). A proposta não exige.
    3. Políticas de RLS em comentarios? A aplicação acessa o banco só pela service_role (seção 5), então as políticas abaixo não afetam o caminho atual. Opções: (a) manter o padrão das outras tabelas, com RLS ativo e sem políticas; (b) incluir as políticas como defesa extra caso um dia o frontend use o token do usuário. A proposta traz as políticas da opção (b), que podem ser removidas.
    4. Moderação: não há denúncia nem remoção por administrador. Se necessário, criar uma coluna oculto BOOLEAN e um papel de moderação em uma issue futura.
    5. Exibição do autor: o comentário exibe perfis.username? Como o backend lê com a service_role, basta fazer o JOIN no código. Se um dia o acesso for direto, a leitura de perfis precisará de política.

    6.4 Onde cada regra é aplicada

    Regra Onde é garantida
    Um comentário por usuário e professor Banco: UNIQUE (usuario_id, professor_id). O backend deve tratar o erro de duplicidade.
    Tamanho do texto (10 a 1000) Banco: CHECK. O backend deve validar antes para devolver mensagem amigável.
    Só o autor edita ou apaga Backend (Flask), pois a service_role ignora o RLS. As políticas só reforçam.
    usuario_id do comentário Sempre tirado da sessão autenticada no servidor, nunca de campo de formulário.

    7. Como recriar o banco

    1. Criar um projeto Supabase vazio.
    2. No SQL Editor, executar o script de docs/migrations/ (e, se aprovado, o bloco de RLS da seção 5).
    3. Copiar .env_example para .env e preencher:
    4. SECRET_KEY: gerar com python -c "import secrets; print(secrets.token_hex(32))".
    5. SUPABASE_URL: URL do projeto (o código remove sufixos como /rest/v1).
    6. SUPABASE_SERVICE_KEY: chave service_role em Project Settings → API. É secreta: não commitar e não expor em templates.
    7. FLASK_DEBUG: 0, ou 1 somente em desenvolvimento local.
    8. Executar o scraper do SIGAA para popular professores, disciplinas e turmas.
    9. A tabela comentarios só entra depois da aprovação da proposta da seção 6.
